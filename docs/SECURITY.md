# Security notes

## What the code does

- **Passwords**: stored the same way as the sxingxian.com admin accounts. The Worker pre-hashes with SHA-256 (domain-separated, NFKC-normalised), and Neon stores `bcrypt(prehash)` at cost 12 via `pgcrypto`. The plaintext never leaves the Worker, bcrypt's 72-byte limit cannot truncate a long passphrase, and hashing runs on Neon instead of the Worker's CPU budget. Policy: 12 to 256 characters, not a common password, does not contain the email name. Unknown emails are checked against a dummy hash so they take the same time.
- **Sessions**: random 256-bit token in an `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` cookie; only its SHA-256 hash is stored. App sessions last 30 days, admin sessions 8 hours.
- **Cross-site requests**: every state-changing API call must carry an `Origin` that matches the host. Webhooks and the OAuth return leg are exempt and authenticate by signature, secret or state instead.
- **Admin**: separate session cookie; password then a time-based code from an authenticator app. Admin routes refuse sessions that have not passed the second factor.
- **Third-party requests from the pages**: fonts and the on-device voice's speech runtime are served by Niko itself. The one exception is the on-device voice's model and voice files, which the browser downloads from Hugging Face (`huggingface.co`, `*.hf.co`) only when someone presses *Download to this device*. The model is checked against a pinned SHA-256 before it is used, and each voice file's size is checked; anything else is refused. These hosts are the only ones besides Niko in `connect-src`.
- **Provider app keys are per account**: each account saves its own Google, Microsoft, Notion and Slack client ID and secret. They are encrypted with `ENCRYPTION_KEY`, used only for that account's sign-ins, never returned to the browser (only the last 4 characters of the client ID are shown), and deleted with the account. Sign-in and token addresses are fixed in code, so saved keys can't point Niko at another server. Slack events are checked with that account's own signing secret.
- **Sign-in lockout**: counted per email and network address together. After 5 wrong attempts in a row that pair is locked for 1 minute, then 2, 4, 8, 16, 32, up to 60. While locked, even the right password is refused. Unknown emails are counted the same way, so a lock does not reveal which accounts exist. Wrong second-factor and recovery codes count too. A separate per-address cap limits guessing across many emails.
- **Single-use codes**: each authenticator time step is accepted once per admin (an atomic database update), so a code that was seen or intercepted cannot be used again.
- **Recovery codes**: ten codes shown once when the second factor is first set up; only their hashes are stored; each works once; an admin can replace the set, which cancels the old ones.
- **Command-line recovery**: `npm run user` (see [DEPLOYMENT.md](DEPLOYMENT.md)) resets a password or second factor and clears locks using the database connection string. There is no recovery path over the web that skips the second factor.
- **Invite only by default**: invites and reset links are single-use, stored hashed, and expire (7 days / 30 minutes; a paid invite stays open until the account is made, a year at most). With open registration, new accounts stay switched off until an admin enables them.
- **Passkeys**: sign-in only, one per registrable domain (`sxingxian.com`, `midnightpoetry.studio`).
- **Attempt limits**: sign-in, admin sign-in, second-factor, invite, reset and setup attempts are limited per email and per IP.
- **Stored credentials**: connection tokens, API keys and second-factor secrets are encrypted with AES-256-GCM using `ENCRYPTION_KEY` before they reach Neon. Removing a connection deletes the row. An account's AI keys are kept together in one encrypted record; a key is never sent back to the browser, and removing one rewrites the record without it. The order of brains may name only that account's own saved keys. When a brain fails, the provider's error text goes to the Worker log only (it can name accounts or limits); during conversations the screen says only whether it was a usage limit, a refused key or no answer. The Test button shows the key's owner the provider's own short message, with anything that looks like a key removed. Voice and speech-in API keys are kept the same way, each in their own encrypted record. Speech in records only after the mic is tapped or “Niko” is heard (the wake word itself is always the device's own recognition), sends one short 16 kHz WAV per request (at most 2 MB, checked on the server) straight on to the chosen service, and never stores it; in their own encrypted record; Azure regions must be a plain name, voice names are limited to safe characters (and escaped in SSML), and redirects from speech services are not followed. A saved key is only ever sent to the address it was saved with: changing a key's address needs the key typed again, and listing a key's models with its saved key uses only its saved address. Admins choose which AI options each account may use (Admin → AI options): a default for everyone, kept in `app_settings`, and one account's changes in `users.ai_access`. Options that are off are not only hidden in the app: the server refuses them wherever they could be used (answering, speaking, listening, painting, Test, adding a key or a server), and skips any key saved earlier for them, so turning an option off cannot be got round from the browser. Keys are kept, not deleted. Admins always have every option, at least one brain stays on for every account, and every change is written to the audit log. New items on Home are off until a person turns them on (Appearance), and an admin can withhold them or limit how often each kind is checked (Admin → New items), for everyone or one account. The server reads a mail, calendar or notes service only when that kind is due under both the person's choice and the admin's limit, ignores repeated asks within 40 seconds, and reads nothing for someone who has not turned it on. What has been shown is remembered per account as item ids and times only (no subjects or contents), for two weeks; for reminders, the titles and start times of that person's events in the next six hours are kept until they start. Every change to the limits is written to the audit log. Image API keys are kept the same way, in their own encrypted record. The user's own servers (model, voice, image and speech-to-text) must have a public https address; their optional key is encrypted like any other, and when a server's address changes, a key not typed again is dropped instead of being sent to the new address (this holds for every saved connection with an address and a key). Pictures: a prompt is plain text, at most 1,500 characters, and is not logged; the picture comes straight back to the browser and is never stored (it lives only in the page's memory until Save keeps a copy on the device). Only pictures are passed on: the server checks the first bytes are JPEG, PNG or WebP (never SVG or HTML), sends them with that type and `nosniff`, and the page shows them as `blob:` images. Keyed requests to image services do not follow redirects. Services that leave the picture at an address are fetched without the key, and only from their own hosts (fal.media, replicate.delivery, bfl.ai, ideogram.ai); Black Forest Labs' and Replicate's polling addresses must be on their own API hosts before the key is sent to them. Each account can make 30 pictures in 15 minutes. Each image service applies its own content rules; a picture one declines is passed to the next service in the order, and the service is not rested for it. Maps: map service keys (and OneMap's account email and password, and Naver's client secret) are kept in their own encrypted record, never sent back to the browser, and sent only to that service's own address (a route server of your own: only to the address it was saved with; changing the service, the address or the OneMap account needs the key typed again). OneMap's short-lived token is kept only in the Worker's memory. Places and routes are found on the server, so the browser gets only the place, the line to draw and the steps; requests to map services do not follow redirects, and errors show only whether it was a limit, a refused key or no answer. The map picture is drawn in the browser by MapLibre (its worker is a file of the app, not a `blob:`) from OpenFreeMap's OpenStreetMap tiles, the only extra address in `connect-src`. With no keys, places come from Photon (komoot's public OpenStreetMap search, one search per request, with Niko's user agent) and directions open in the local maps app. The lists may name only that account's saved services and the built-in map. Which country's list is used comes from built-in borders (country-coder, no outside service). Each account can look up 40 maps in 10 minutes. Admins can turn maps off, or any one map service, like the other AI options.
- **Payments**: Stripe Checkout takes card and PayNow details on Stripe's own page; Niko never sees them. Niko treats something as paid only when Stripe says so: a webhook whose `Stripe-Signature` checks against `STRIPE_WEBHOOK_SECRET` (HMAC-SHA256, at most 5 minutes old), or Niko asking Stripe's API about a Checkout itself. The page someone returns to after paying is never trusted on its own. A payment must match the price fixed when the invite was sent or the sign-up started (amount and currency), a plan is charged at the account's kept plan prices if it kept them when prices changed (stored on the account, set only by an admin: in Users → Prices, or by the choice made when saving default prices; changes are audited, and changing a running plan's price uses Stripe with no proration, so nothing is charged or refunded that day), else at the current ones, and each Stripe event is applied once (event ids are recorded). Refunds, plan cancellation and unlocks change Stripe first and only then the account, so a failed Stripe call leaves both as they were. Admins and accounts made before payments never need to pay; everyone else needs time left (paid, free or unlocked), a live plan, or lifetime, and the server refuses every app route except `/api/me` and `/api/billing` without it (HTTP 402). Stripe's secret keys, one for test mode and one for live, are Worker secrets only, never stored in the database or sent to the browser. Connect (Admin → Payments) uses a key to create Niko's webhook endpoint, billing-page settings and products in that Stripe mode; the webhook's signing secret, shown by Stripe only once, is kept in the database encrypted with `ENCRYPTION_KEY` (a signing secret set as a Worker secret takes its place if present). Connect replaces Niko's earlier endpoint at the same address and touches nothing else in the Stripe account. The admin portal only chooses which mode new payments use (recorded in the audit log), and only a mode whose keys are set and have the right prefix: a test key is never used as a live one or the other way round. Each payment, plan and Stripe customer is recorded with its mode, so refunds, plan changes and the billing page always use the keys of the mode they were made in. A webhook is accepted only if one mode's signing secret matches and the event's own `livemode` agrees. While test mode is on, a test card gets real access to Niko; the admin portal and the pay screens say so throughout.
- **Designs**: what a design costs, what “All designs” covers and the pro-rated price a bundle owner pays for a new design are worked out on the server from the admin's settings, never from what a screen sends; each design Checkout is recorded with the designs and amount Niko fixed, and a payment counts only if Stripe confirms that exact amount for that account, once. Whether an account may use a design is checked on the server when it is chosen and every time the app loads (the core falls back to Nebula otherwise); the design can't be set through the ordinary settings save. Designs that were paid for stay with the account even after the admin stops offering them; an admin can take back only designs they gave. Niko Pro is added to the account's own plan subscription with `payment_behavior=error_if_incomplete`, so if the card can't pay nothing is added, and it is offered only on an active monthly or yearly plan (not during pay-once time). Removing it credits unused time through Stripe.
- **Backgrounds**: the same rules as designs, kept separately (`background_owned`, `background_checkouts`, Checkouts marked `kind: background`): prices, the bundle and pro-rated new backgrounds are worked out on the server; a payment counts only for the exact amount Niko fixed for that account, once; whether an account may use a background is checked when it's chosen and every time the app loads (Glow otherwise), and it can't be set through the ordinary settings save. Paid backgrounds stay after they stop being offered; an admin can take back only gifts. Niko Pro is the one add-on from designs; whether it covers backgrounds is the admin's setting.
- **Invite codes**: each invite carries a 6-character code from an alphabet without look-alikes (31 characters, about 887 million combinations), sent in the same email as the link and shown once to the admin. Only a hash tied to that invite is stored. Five wrong codes lock the invite until the admin sends a new code (which also replaces the link); guesses are also limited per network address. The right code sets a random pass in an `HttpOnly`, `Secure`, `__Host-` cookie on that browser (stored only as a hash); paying and creating the account need it. Because the code travels with the link, it protects against a forwarded link or an email preview scanner, not against someone who can read the whole email.
- **Open sign-up**: the account is made switched off; a 6-digit code emailed to the address (15 minutes, 5 tries, at most 3 new codes per 15 minutes) proves the email before any payment. The browser keeps its place with a random token in an `HttpOnly` `__Host-` cookie (only its hash is stored), never in page storage. A sign-up with an email that already has an account answers the same way as a new one, so it can't be used to find out who has an account; the owner of that email gets a note instead of a code. Paid sign-ups stay off until an admin switches them on, and unpaid ones are deleted after 7 days by a background job that runs at most once an hour, started by ordinary traffic (no cron trigger).
- **Knowledge on “This device”**: files kept on a device are read, stored and searched in that browser only (Cloudflare reading is not used for them). Each account has its own IndexedDB database, and every record (file names, text, rows, search numbers) is encrypted with AES-256-GCM, bound to its record by additional data, using a key the server derives from `ENCRYPTION_KEY` and the account (HMAC-SHA-256, `GET /api/knowledge/device-key`, `no-store`, only for accounts allowed the device place). The key is kept only in the page's memory and forgotten when the account changes, so another person on the same computer can't read the files and nothing can be read while signed out. With a question, the browser sends at most 10 matching pieces (2,000 characters each) and 6 table outlines; the server checks and caps them and shows them to the AI as untrusted file content, like files kept in Niko. Spreadsheet look-ups for these tables are run by the browser with the same fixed operations as the server, and their results (at most 3, 4,000 characters each) are also marked untrusted. Telegram replies never use device files. The optional search model (multilingual-e5-small) is downloaded from Hugging Face only when the person presses *Download to this device*; the model and tokenizer are checked against pinned SHA-256 fingerprints and sizes, the two settings files must be small JSON, any other address is refused, and the runtime is Niko's own pinned ONNX Runtime files in `/app/ort/`. Rotating `ENCRYPTION_KEY` makes files kept on devices unreadable (people add them again).
- **What Niko learned**: learning is off until the admin turns it on for a person (AI options · Knowledge), and the person can pause it. Notes are kept in the Knowledge database (`kn_learned`, filtered by account, at most 1,000 per person and 500 taught matches), or encrypted on the device like files when the person's Knowledge is kept there. The AI can only *ask* to save a note with a `[[learn:…]]` tag; the server keeps it only when its words come from the person's own message (or, for a name or correction, one side from the message just before), and never from drafts. So text in an email, message, file or web page can't teach Niko anything. Anything that looks like a password, code, or card or account number is refused, even when asked. Taught matches ("That's the one" / "Not this one") come only from the person's own tap or voice in the signed-in app, point at a piece of one of their own files (checked against the account when used), and go when the file is removed. Notes are shown to the AI as the user's own notes and can never approve sending, paying or deleting. The admin sees counts only. Learning on or off and Forget everything are written to the audit log.
- **Situations, playbooks, habits and quiet mode**: with “Use my calendar, the time and my location” on (only when learning is in the person's plan), a situational question gets the time, the meeting on now and the next event from the briefing Niko already reads, and a location rounded to about 1 km only when the person shared it for a map in the last five minutes. None of it is stored. A playbook is saved only when the person confirms (“that's right”) or corrects Niko's last answer to the situation they asked about. A note about another person is saved only from the person's own words or their yes to Niko's offer, and a note with judging words (“unreliable”, “liar”…) is refused. Situational answers never take an action: sending keeps its confirm and countdown. Habits are counted from the app's own watchers (a trip under 1 km switched to walking, kept as a hash of the place and the day; the inbox opened on a weekday morning, kept as the date), suggested once, kept only with a yes, and deleted after 60 days if never confirmed. Habits said yes to are listed with the account (`users.knowledge.habits`) so the app can apply them. Quiet mode (asked for, or a meeting on the calendar now) speaks nothing and turns the microphone off, including wake-word listening, until it is turned off by a tap or typing.
- **Sending**: the server, not the browser, enforces the rule. A voice-initiated send is refused unless the conversation already has an incoming message, and cannot be confirmed before its 10 seconds are up. A send is claimed atomically so it cannot go out twice.
- **Files**: relayed in request memory, 20 MB limit, never written to storage. The audit log records name, size, time and recipient only.
- **Browser (Niko's browser)**: the browser runs on a browser service (Cloudflare Browser Run), never on the person's device. The Cloudflare token is connected in the admin portal with a fresh authenticator code, sealed with `ENCRYPTION_KEY`, never sent to any browser and never shown again. Niko's server opens and closes browsers and hands the device a short-lived pass (a signed Live View link, good for starting a connection for one minute, only `wss://*.browser.run`); the live picture, taps and typing then go straight between the device and the service, so a password typed during a hand-off never passes through Niko's server. A Durable Object per person keeps one open browser and closes it when the day's minutes run out or the device stops checking in.
- **Niko driving**: the AI sees an outline of the page: password and card fields are listed without their values (only whether they are filled), and the server drops any values a device sends anyway. Page text reaches the AI marked as untrusted; pages that try to give orders are flagged and ignored. After the AI answers, the server decides (never the AI): passwords, card fields, pay or buy buttons, payment frames and "are you human?" checks are handed to the person; creating an account, signing in, sending a form, agreeing to terms, downloading and going to a new site wait for the person's OK. An OK is a token signed by the server for exactly that action on that browser, for two minutes, used once (the Durable Object remembers used tokens).
- **Stay signed in and sign-in codes**: a person can keep a site's sign-in after signing in there. Only that site's cookies are kept (checked on the server too), sealed with `ENCRYPTION_KEY` in `browser_signins`, returned only to that person's own browser session, and deleted on Forget or when the admin switches "Stay signed in" off. Sign-in codes are looked for only in mail from that site in the last 10 minutes, shown to the person, entered only after they say so, and never stored or sent to the AI. Code fields are treated like password fields: their values are never read.
- **Other browser services** (the account's own server, a hosted service, a person's own): public https/wss addresses only, tested before saving, keys sealed and never sent to a device. The account's services need a fresh authenticator code to save or remove. The device connects to Niko's own address with a one-minute pass for one tab. The person's BrowserKeeper holds the connection to the service and passes on only that tab's messages. Commands for the whole browser (other tabs, other browser contexts, closing it) are refused. Each browser has its own browser context, so people sharing a server never share cookies, and the context is disposed when the browser closes. A hosted service's operator can see its pages, including what is typed in a hand-off; Settings and the admin portal say so.
- **Browser sites**: only public http(s) sites (no number addresses, local names or private ranges); sites the admin blocks are refused by the server for Niko's actions and checked on the device before every page load. Downloads go straight to the device; the activity log records only that a file was downloaded. "What Niko did" keeps sites and steps, never typed text, page contents or pictures of pages, for as long as the person chose.
- **Outbound addresses** supplied by users (webhooks, custom AI, calendar links) must be public `https` URLs; localhost and private ranges are refused.
- **Changing a password while signed in** needs the current password (5 tries per 15 minutes, failures audited). It signs out every other session, including the admin portal, keeps the current one, and emails the account. A forgotten current password goes through the emailed reset link instead.
- **Calendar links** (iCal): each account keeps a list (20 by default; the admin sets the limit for everyone or per account, at most 50). The whole list is one encrypted connection record. A private address is never sent back to the browser in full (only its server and file name); a public one is. Each address is read once to check it before it is saved, at most 30 checks per account per 15 minutes, and feeds are fetched at most every 10 minutes, six at a time. Adding, changing and removing a calendar are written to the audit log without the address. A bare Google calendar ID is read only through Google's public address for it, so it can never reach a private calendar.
- **Google calendars** (after Google sign-in, read-only scope): the list comes live from Google; which ones are read is kept in the connection's encrypted secret (shared calendars' IDs are often people's email addresses). Only calendars actually on that account can be chosen, names come from Google, the same per-account limit applies, and the main calendar keeps its event ids.
- **Mail servers (IMAP/SMTP)**: a public server name only (no IP addresses or local names), always encrypted: implicit TLS on 993/465, or STARTTLS on 143/587 that must succeed (certificates are always checked). App passwords are encrypted like other secrets. The inbox is opened read-only for listing and reading. Reply headers have line breaks removed so a subject cannot add headers, and message bodies are dot-stuffed. A test-only switch allows plain text to 127.0.0.1 for the test suite; it is never set by the app.
- **Opened content**: notes, emails and events are turned into plain text on the server; provider HTML never reaches the browser. Links out are shown only when they are https to the provider's own site.
- **AI prompt**: mail, events, notes and chats are passed to the model inside a block marked as untrusted, with an instruction not to follow anything inside it. The model has no ability to send; it can only draft.
- **Headers**: HSTS, a strict Content-Security-Policy (`img-src` allows `blob:` for pictures made in the page; `script-src 'self' 'wasm-unsafe-eval'`: WebAssembly may run, for the on-device voice, but `eval()` of scripts may not), `frame-ancestors 'none'`, `nosniff`, and microphone and location limited to the same origin. Location is asked for only when a weather question is asked with a weather service connected; it is rounded to about 1 km in the browser, rounded again on the server, used for that one forecast request to Open-Meteo, and never stored or logged. For maps, Niko first says why, then the browser asks; if the person declines, Niko uses the Worldwide list and does not ask again in that visit. The location (to about 10 m, for the route's start) is kept in the page's memory for up to five minutes, sent only with that map request, used to find the country and start the route, and never stored or logged; for Chinese services it is converted to their coordinates before it is sent. Place names Niko looks up are reduced to letters, digits and simple punctuation before they are sent to Open-Meteo's geocoder. The app is cross-origin isolated (`Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp`, `Cross-Origin-Resource-Policy: same-origin`): no other site's window keeps a handle on it, it loads nothing from other sites except the on-device voice files (fetched with CORS), and the on-device voice can use several processor cores.
- **Voice servers**: a user's own voice server must be a public https address; redirects are not followed, and replies that are not audio, or over 8 MB, are refused. Server-made speech is limited to 150 lines per account per 15 minutes, since Cloudflare's voice uses the account's shared free allowance.

## Known gaps and risks

- **Not reviewed or penetration-tested.** Treat this as a first implementation.
- **Voice is not authentication.** "Respond only to my voice" is not built. Anyone within earshot can say "Niko, send it" for a reply in an existing conversation; the countdown is the only safeguard.
- **Prompt injection** from email, chat or web page content is reduced, not eliminated. In the browser, the server-side rules (hand-offs and OKs) are the real control.
- **Niko's browser on the device**: the device holds a full pass to its own browser while it is open (that's how the person drives). The admin's blocked sites are enforced on the device for the person's own browsing, so someone who modifies the app on their own device could get past them; the server still refuses them for Niko's actions. Niko never sends without your approval, which is the real control.
- **The repository is public.** No secrets are in it; keep it that way. Anyone can read how the service works.
- **Attempt limits are stored in Postgres** and are approximate under bursts. Add a Cloudflare rate-limiting rule on `/api/auth/*` and `/api/admin/*` for a firmer limit.
- **Telegram bots** see only messages people send to the bot. The Telegram file link is fetched with the bot token on demand; the token never reaches the browser.
- **Audit log and chat history** grow without pruning. Add retention if this runs for long.
